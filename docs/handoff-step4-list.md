## 1. 주 과업과 화면의 계약

**주 과업**: 41편을 훑어 목표한 글 하나에 도달한다.

성공의 조건은 셋뿐입니다. 나머지 결정은 전부 이 셋에서 파생됩니다.

1. **훑기** — 한 화면에 최대한 많은 글이, 서로 구별되는 형태로 놓인다
2. **걸러내기** — 검색·카테고리·정렬이 즉시 반응하고, **지금 무엇이 걸려 있는지** 항상 보인다
3. **되찾기** — 그 상태가 **URL에 남아** 공유·뒤로가기·새로고침에서 복원된다

3번은 이 프로젝트의 1순위 과제(딥링크 복구)와 같은 요구입니다. 목록 화면만 상태가 휘발되면 일관성이 깨집니다.

#### 2-4a. 🔴 `role="radiogroup"` 반려 — 구현이 옳았습니다 (2026-08-13 신설)

**이 절은 되돌림 방지가 목적입니다.** 명세가 `radiogroup`을 적어 뒀고 구현은 `group`을 썼습니다. 구현이 반려한 것이고, **QA가 그 반려를 타당 판정**했습니다. 근거를 남겨 두지 않으면 다음 사람이 "명세 위반"으로 보고 되돌립니다.

| | 이 문서의 이전 기술 | **현재 정본** | 구현 |
|---|---|---|---|
| 컨테이너 | ~~`role="radiogroup"`~~ | **`role="group"`** + `aria-label="정렬"` | ✅ 이미 `group` |
| 각 옵션 | ~~`role="radio" aria-checked`~~ | **`<a>` 그대로**(role 덮어쓰지 않음) + 활성에 `aria-current="true"` | ✅ 이미 그러함 |

**반려 근거 3가지**

1. **`radiogroup`은 조작법을 약속합니다 — 그런데 그 조작법이 없습니다.** 라디오 그룹은 **화살표 키 이동 + 로빙 `tabindex`**(그룹 전체가 탭 스톱 1개)를 전제하는 역할입니다. 링크에 role만 얹으면 보조기술은 "화살표로 고르세요"라고 안내하는데 **실제로는 아무 일도 일어나지 않습니다.** 잘못된 안내는 안내가 없는 것보다 나쁩니다
2. **role을 덮어쓰면 "링크"라는 사실이 사라집니다.** 이 옵션들은 진짜 링크(`/posts?sort=oldest`)이고, 사용자는 **새 탭으로 열거나 주소를 복사**할 수 있어야 합니다. `role="radio"`는 그 관용을 감춥니다
3. **URL이 곧 상태이므로 `aria-current`가 사실에 맞습니다.** `aria-checked`는 *"내가 이 위젯에서 고른 값"*이고, `aria-current`는 *"지금 보고 있는 것이 이것"*입니다. 이 화면의 정렬은 **폼 입력이 아니라 현재 위치**입니다(§4의 「상태는 URL」 원칙). 카테고리 칩(§10-2)이 이미 같은 이유로 `aria-current`를 씁니다 — **한 화면 안에서 같은 성격의 컨트롤이 다른 계약을 갖지 않게 됩니다**

> `role="group"`을 남기는 이유는 **이름 때문**입니다. 두 링크가 `정렬`이라는 하나의 묶음이라는 것을 전달해야 하고, `group`은 조작법을 약속하지 않으므로 1번 문제가 생기지 않습니다.

> **적용 범위**: `SortSegment`는 **세 화면이 공유하는 한 컴포넌트**입니다 — `/posts`·`/tags/:tag`(`최신순`/`오래된순`)와 `/tags`(`빈도순`/`이름순`). 이 계약은 세 곳 전부에 적용되며, `handoff-step6-tags-archive.md` §2-1b·§12-2도 2026-08-13에 함께 정정했습니다. **한쪽만 고치지 마십시오.**

## 3. 🔴 검색 · 필터 · 정렬 로직 계약

### 3-1. 검색 대상 — 무엇을 뒤지는가

**대상 4필드**: `title` · `keywords[]` · `category` · `description`

**본문은 대상이 아닙니다.** 실측 근거:

| 항목 | 실측 |
|---|---|
| 41편 본문 총 문자 수 | **191,417자** |
| UTF-8 바이트 추정 (한글 혼합) | **380 KB ~ 570 KB** |
| 현재 `posts-data.json` | 15 KB (gzip 2.9 KB) |
| 색인 포함 시 | 약 **25~40배** 증가. gzip 후에도 +100 KB 이상 |
| 현재 JS 번들 | 이미 단일 청크 481 KB gzip |

`/posts` 진입마다 이 파일을 받습니다. 41편 규모에서 본문 검색이 주는 이득보다 비용이 큽니다. `agent-log/product.md` #26이 이미 **백로그**로 판정한 항목이며 이 문서도 같은 결론입니다.

**대신 필수**: 검색 범위를 사용자가 알 수 있어야 합니다. 입력 아래 `제목·태그·카테고리에서 찾아요`를 **항상 노출**합니다(STEP 1 §9 확정 문구). `description`은 1편뿐이라 안내 문구에 넣지 않습니다 — 공짜로 포함하되 광고하지 않습니다.

### 3-2. 매칭 규칙

```
정규화(문자열):
  NFC 정규화 → toLowerCase() → trim() → 내부 연속 공백 1칸으로 축약

토큰화(질의):
  정규화된 질의를 공백으로 분리 → 빈 토큰 제거 → tokens[]
  tokens 가 비면 검색 조건 없음(전체 통과)

포스트 1건의 검색 대상 문자열(haystack):
  정규화( title + "\n" + keywords.join(" ") + "\n" + category + "\n" + description )

일치 판정:
  tokens.every(t => haystack.includes(t))     // 토큰 간 AND, 필드 간 OR
```

| 규칙 | 값 | 근거 |
|---|---|---|
| 부분 일치 | **O** (`includes`) | 한국어는 어절 경계가 없고, `ReactHook_useMemo` 같은 결합 제목이 실재. 단어 경계 매칭이면 `usememo`가 안 잡힘 |
| 대소문자 | **무시** | 태그에 `JavaScript`와 `Javascript`가 **둘 다 존재**. 무시하지 않으면 같은 태그가 갈림 |
| 유니코드 정규화 | **NFC** | macOS 입력기가 NFD를 만들 수 있고, `.md` 파일명·프론트매터 출처가 섞여 있음. 정규화 없으면 `한글`이 안 잡히는 사고가 재현 불가 형태로 발생 |
| 다중 키워드 | **AND** | `react hook`은 "둘 다 있는 글"을 기대. OR이면 react만 있는 14건이 다 나와 필터가 무의미 |
| 필드 간 | **OR** | 토큰이 제목에 있든 태그에 있든 통과. 토큰마다 다른 필드에서 맞아도 됩니다 |
| 최소 길이 | **없음** | 1글자 검색 허용 (`훅`, `합`). 41편 규모에서 결과 폭주 위험 없음 |

### 3-4. 정렬 — 🔴 타이브레이커 필수

`date`는 **날짜만 있고 시각이 없습니다.** 그리고 **41편 중 25편이 같은 날짜를 공유**합니다.

| 날짜 | 편수 |
|---|:--:|
| 2023-04-13 | 5 |
| 2023-02-26 | 4 |
| 2023-01-10 | 4 |
| 2022-12-27 | 4 |
| 그 외 4개 날짜 | 각 2 |

날짜만으로 정렬하면 **같은 날짜 묶음의 순서가 정의되지 않습니다.** 페이지 경계에 그 묶음이 걸리면 페이지를 오가는 사이 **같은 글이 두 번 보이거나 한 편이 사라질 수 있습니다.**

```
정렬 키 = [date, slug]
  최신순(desc)    : date 내림차순, 동률이면 slug 내림차순
  오래된순(asc)   : date 오름차순, 동률이면 slug 오름차순
비교는 localeCompare 가 아니라 문자열 < > 로 충분 (date 는 고정폭 ISO, slug 는 ASCII)
```

`slug`는 41편 전부 고유하므로 전순서가 보장됩니다.

### 3-5. 조합 규칙 — 검색 × 카테고리 × 정렬

```
표시목록 = 정렬( 카테고리필터( 검색필터( 전체 41편 ) ) )
표시페이지 = 표시목록.slice( (page-1)*20, page*20 )
```

- 검색과 카테고리는 **AND**입니다. `?q=python&category=Survey` → Python이면서 Survey인 글
- 카테고리 칩의 **개수 배지는 항상 전체 기준 고정값**(전체 41 / Study 30 / Survey 9 / Activity 2)입니다. 검색어에 따라 바뀌지 않습니다
  - 근거: 배지가 요동치면 "이 칩을 누르면 몇 개가 나오는가"가 아니라 "지금 몇 개인가"가 되어, 칩이 **필터 선택지가 아니라 결과 표시**로 변질됩니다. 현재 결과 수는 목록 헤더가 이미 말합니다
- 정렬은 결과 집합에만 작용하며 필터에 영향을 주지 않습니다
- **조건이 하나라도 바뀌면 `page`를 1로 되돌립니다** (§4-3)

### 3-6. 하이라이트 — 🔴 시안 **수정**

시안은 **제목만** 하이라이트합니다. 실측하면 이게 깨집니다.

| 질의 | 결과 | 그중 제목에 일치 문자열이 **없는** 행 |
|---|:--:|:--:|
| `react` | 14건 | **6건** |
| `browser` | 3건 | **3건 (전부)** |
| `hooks` | 3건 | **3건 (전부)** |
| `typescript` | 5건 | 3건 |

`browser`를 검색하면 **세 행 모두 아무 데도 강조가 없습니다.** 사용자 입장에서 "왜 이게 결과인가"를 알 수 없습니다.

**확정 규칙**

1. **제목** — 각 토큰의 모든 출현 구간을 `<mark>`로 감쌉니다
2. **태그 칩** — 토큰이 포함된 태그 칩에 액센트 처리(§5-1 태그 칩 상태표)
3. **🔴 일치한 태그가 노출 3개 밖에 있으면 앞으로 끌어올립니다** — 일치 태그를 먼저 배치하고 남은 자리를 원래 순서로 채웁니다. `+N` 개수는 그에 맞춰 재계산
   - 실측: `webxr`·`browser`·`nextjs` 검색 시 각 1건이 숨은 태그에서만 일치. 이 규칙이 없으면 그 행은 영구히 이유 불명
4. **카테고리 칩(행 우측)** — 토큰이 카테고리명과 일치하면 액센트 처리
5. 토큰이 여러 개면 **각각** 독립적으로 위 1~4를 적용

**하이라이트 구현 규칙**

- 요소는 `<mark>`. `<span>` + 배경색이 아닙니다 (시안은 span)
- 스타일: `background: var(--color-accent-subtle); color: var(--color-accent-text); border-radius: var(--radius-xs); padding: 0 1px`
  - 브라우저 기본 `mark` 스타일(노랑 배경 + 검정 글자)을 **반드시 덮어씁니다.** 안 덮으면 다크 모드에서 형광 노랑 블록이 됩니다
- 대비 실측 (§10에 재게재): 라이트 4.81:1 / 다크 7.74:1 — 본문 기준 4.5:1 통과
- **스크린리더**: `<mark>`는 NVDA·VoiceOver 기본 설정에서 낭독되지 않습니다. **그대로 둡니다.** `aria-label`이나 시각 숨김 텍스트로 "일치"를 덧붙이면 제목 한 줄이 3~4토막으로 끊겨 낭독되어 제목을 알아들을 수 없게 됩니다. 일치 사실은 결과 목록에 있다는 것으로 이미 전달됩니다
- 대신 **결과 수를 `aria-live`로 알립니다** (§10-3)

**정규화와 인덱스**: 매칭은 정규화 문자열에서 하지만 **표시는 원문**이어야 합니다. 소문자화는 길이를 바꾸지 않지만 **NFC 정규화는 바꿀 수 있습니다.** 하이라이트 구간을 계산할 때는 `title`을 NFC 정규화한 문자열로 인덱스를 구하고, **그 NFC 문자열을 그대로 렌더**하십시오(원문으로 되돌리지 마십시오). NFC는 사람이 보는 결과가 동일합니다.

```html

- `<form>`으로 감싸는 것은 시각 효과가 아닙니다 — **스크린리더에 검색 폼(landmark `search`)으로 노출**되고, Enter가 브라우저 기본 동작으로 처리됩니다. `§10-2`가 이미 `<form role="search">`를 요구하고 있고 구현도 그렇습니다. **`onSubmit`에서 `preventDefault()` 뒤 아무것도 하지 않던 것을 `navigate`로 바꾸는 것이 이 변경의 최소 형태**입니다

#### 3-8-4a. 🔴 조합 중에 들어온 빈 값은 「지우기」가 아닙니다 — 가드는 **커밋 지점**에 둡니다 (2026-08-02 신설 · 구현 반영 완료 `773d7aa2`)

> **규정**: 한글 IME **조합 중**에 입력값이 빈 문자열로 들어오면 **값도 바꾸지 않고 커밋도 하지 않습니다.** `§3-8-4`의 「비면 즉시 전체 목록」은 **조합 중이 아닐 때**의 규칙입니다.

**무엇을 막는가** — 조합 중 `Escape`를 누르면 사용자가 원하는 것은 **조합 취소**뿐입니다. 그런데 `type="search"`의 **네이티브 Escape 클리어**가 함께 발화해 입력창을 통째로 비웁니다. 그 빈 값을 `§3-8-4`로 태우면 ①치던 글자가 전부 사라지고 ②`q`가 URL에서 제거되며 ③히스토리까지 한 칸 쌓입니다. **입력 유실입니다.** QA가 CDP `Input.imeSetComposition`으로 재현했습니다.

**🔴 왜 `onKeyDown`이 아니라 커밋 지점인가** (이게 이 절의 핵심입니다 — 이 문단이 없으면 다음 사람이 가드를 다시 `onKeyDown`으로 옮깁니다)

| | |
|---|---|
| **처음 시도: `onKeyDown`의 `isComposing` 가드** | 🔴 **관측된 두 경로 모두에서 아무 일도 하지 않았습니다.** |
| **진짜 원인** | 앱 핸들러가 아니라 **브라우저입니다.** `type="search"`의 네이티브 Escape 클리어는 **우리 `onKeyDown`을 거치지 않고** 곧장 빈 값 `onChange`로 들어옵니다. 키 이벤트에 문을 세워 두면 그 문 옆으로 지나갑니다 |
| **그래서** | 가드는 **모든 경로가 반드시 통과하는 지점** — 입력 변경 → 커밋으로 이어지는 **한 곳**에 있어야 합니다. 경로를 하나씩 막는 대신 **목적지를 막습니다** |

**부수 규정 — DOM 값을 직접 되돌립니다**

커밋만 막고 state를 그대로 두면 **화면이 빈 채로 남습니다.** DOM은 이미 네이티브 클리어로 비워졌는데, state가 안 바뀌면 React는 리렌더하지 않고 **controlled value를 되돌려주지 않습니다**(실측). 그래서 가드 안에서 `input.value`를 직전 값으로 복원하고 캐럿을 끝에 둡니다. 🔴 **이 복원 코드를 「불필요한 DOM 직접 조작」으로 보고 지우지 마십시오** — 지우면 화면만 빈 채로 남는 형태로 결함이 돌아옵니다.

**정상 입력을 막지 않는 이유** — 조합 중에 실제로 글자를 지우면 **값이 빈 문자열이 되기 전에 조합이 끝납니다.** 가드 조건(`조합 중 && 값이 빔`)은 네이티브 클리어 경로에서만 참이 됩니다.

**되돌림 방지** — 이 가드가 「명세에 없는 코드」로 보여 지워지는 것을 막으려고 이 절을 신설했습니다. 되돌리려면 위 표의 「진짜 원인」을 먼저 반박해야 합니다. 검증은 `§15` 「검색 실행 모델」 블록의 조합 중 항목이 지킵니다.

#### 3-8-5. URL → 입력창 동기화 — 언제 덮어쓰는가

| 상황 | 입력창을 덮어쓰나 |
|---|:--:|
| 최초 로드 · 공유 링크 진입 (`/posts?q=react`) | ✅ |
| **뒤로/앞으로 가기로 `q`가 바뀜** | ✅ **미확정 입력을 버리고 덮어씁니다** |
| 뒤로/앞으로 가기인데 **`q`는 그대로**(카테고리·정렬·페이지 이동의 POP) | ❌ **미확정 입력을 유지합니다** (2026-08-02 정정 — 아래) |
| 헤더 ⌘K에서 검색해 이 화면으로 진입 | ✅ |
| 이 화면의 커밋이 만든 URL 변경 (에코) | ❌ **덮어쓰지 않습니다** |
| 카테고리·정렬·페이지 변경으로 URL이 바뀜 | ❌ (`q`가 안 바뀌므로 애초에 발동하지 않음) |

- 🔴 **"내가 쓴 값인가"를 판별해야 합니다.** 현재 구현의 `writtenQueryRef` 방식이 정확히 이 판별이고, **그대로 유지**합니다. 없으면 두 효과가 서로를 덮어 사용자가 친 글자가 지워집니다
- **뒤로가기가 미확정 입력을 이기는 이유**: 히스토리 이동은 사용자가 명시적으로 요청한 것이고, 그 결과 화면(`q=react`)과 입력창(`reactq`)이 다르면 **입력창이 거짓말을 합니다**. 커밋 기반에서 입력창은 "URL의 편집 중인 사본"이므로, 원본이 바뀌면 사본을 새로 뜹니다
- 🔴 **덮어쓰기의 트리거는 「POP인가」가 아니라 「`q`가 바뀌었는가」입니다** (2026-08-02 정정 · 표 2행 신설 — review 지적 채택). ~~원래 이 표는 POP을 무조건 덮어쓰기로 적었습니다~~ **→ 표현이 과하게 넓었습니다.** 위 근거는 *"원본이 바뀌면 사본을 새로 뜬다"*이므로 **원본이 안 바뀐 POP에는 애초에 적용되지 않습니다.** 카테고리 이동을 뒤로가기로 되돌리는 것은 `q`를 건드리지 않으므로 입력창이 거짓말을 하지도 않습니다 — 그 상황에서 초안을 지우면 **사용자가 잃을 이유가 없는 입력을 잃습니다.** 현재 구현(`params.q !== writtenQueryRef.current`일 때만 덮어씀)이 정본이고, 표 5행(카테고리·정렬·페이지 변경)과도 이제 규칙이 하나입니다

#### 3-8-6. 0건에서 다시 검색하기 — 조작 횟수

| 복구 경로 | 조작 |
|---|:--:|

#### 3-8-7. 헤더 ⌘K와의 관계 — **이미 커밋 기반. 바꾸지 않습니다**

`HeaderSearch.tsx` · `SearchPanel.tsx` 모두 `<form onSubmit>` → `navigate(buildSearchResultPath(query))`이고, 소스 주석도 *"확정은 제출(Enter)이 합니다"*라고 적혀 있습니다. **⌘K는 처음부터 옳았고, `/posts`만 어긋나 있었습니다.**

정합 후 등가:

```
⌘K에서  react + Enter   →  /posts?q=react
/posts에서 react + Enter →  /posts?q=react     ← 같은 URL · 같은 화면 · 히스토리 1건
```

- ⌘K 패널은 **결과를 나열하지 않고 개수만 표시**하며 오버레이 안에서 일어나 문서 높이에 영향이 없습니다. 패널 안의 개수가 타이핑 중 갱신되는 것은 **이번 범위 밖이며 변경하지 않습니다** — 오버레이 안에서는 "몇 건 나올지 미리 보여주는" 것이 실행 전 예고로 유효하고, 레이아웃 시프트도 0으로 측정됐습니다
- 두 화면의 역할이 이렇게 갈립니다: **⌘K = 실행 전 예고 + 실행**, **`/posts` = 실행 결과의 영속 화면**. `§2-3`의 "결과 화면은 하나"가 이렇게 성립합니다

## 4. 🔴 URL 쿼리 동기화

### 4-1. 판정 — **필수**

| 판단 재료 | 결론 |
|---|---|
| 필터된 목록을 링크로 공유 | `/posts?category=Study`, `/posts?q=react`를 보낼 수 있어야 합니다. 이게 안 되면 "Study 글 모아둔 링크"를 줄 방법이 없습니다 |
| 뒤로가기 | 검색 → 글 상세 → 뒤로가기에서 **검색어가 살아 있어야** 합니다. 없으면 41편 목록 처음으로 돌아가고, 사용자는 검색어를 다시 칩니다 |
| 딥링크 일관성 | 이 프로젝트의 1순위가 딥링크 복구입니다. 목록만 상태가 URL 밖에 있으면 **같은 사이트 안에서 원칙이 갈립니다** |
| 프리렌더 영향 | 쿼리는 클라이언트 처리라 **프리렌더 대상이 늘지 않습니다** (`/posts/index.html` 하나 그대로). 비용이 사실상 0 |
| 이미 있는 것 | `Pagination.tsx`가 이미 `?page=`로 `navigate` 합니다. 나머지 3개만 같은 방식으로 맞추면 됩니다 |

### 4-2. 파라미터 규격

| 키 | 값 | 기본값 | 기본값일 때 |
|---|---|---|---|
| `q` | ~~검색어 원문~~ → 🔴 **트림된 검색어** (`encodeURIComponent`, `§4-2a`) | `""` | **키 자체를 뺍니다** |
| `category` | `Study` \| `Survey` \| `Activity` — **저장된 대소문자 그대로** | 전체 | **키 자체를 뺍니다** |
| `sort` | `oldest` | `latest` | **키 자체를 뺍니다** |
| `page` | `2` 이상의 정수 | `1` | **키 자체를 뺍니다** |

**기본값은 URL에 쓰지 않습니다.** `/posts?q=&category=&sort=latest&page=1`가 아니라 `/posts`가 정규형입니다. 링크를 붙여넣을 때 지저분하고, 같은 화면에 URL이 여러 개 생기는 것을 막습니다.

`sort` 값이 `desc/asc`가 아니라 `latest/oldest`인 이유: 사용자에게 보이는 URL은 UI 라벨(`최신순`/`오래된순`)과 대응해야 읽힙니다. 내부 정렬 방향과는 별개입니다.

**예시**

```
/posts                                    전체 · 최신순 · 1페이지
/posts?category=Study                     Study 30편
/posts?q=react                            검색 14건
/posts?q=react&category=Study             교집합
/posts?sort=oldest&page=2                 오래된순 2페이지
/posts?q=react%20hook                     다중 키워드
```

#### 4-2a. 🔴 `q`는 **트림해서 씁니다** — 「원문」 규정 폐기 (2026-08-02 재판정 · ~~🔴 구현 미반영~~ **→ `6c1aeb8e` 반영 완료**)

원래 이 표는 `q`를 **「검색어 원문」**으로 규정했고 구현은 그 규정을 따릅니다. **그 규정을 폐기합니다.**

**폐기 근거**

| | |
|---|---|
| **근거가 문서에 없습니다** | 문서 전체를 훑어도 `q`를 원문으로 두는 이유가 어디에도 적혀 있지 않습니다. 소스의 타입 주석이 같은 문구를 반복할 뿐입니다. **지킬 이유가 기록되지 않은 규정입니다** |
| 🔴 **이 절 자신의 원칙을 깹니다** | 바로 위 문단이 *"같은 화면에 URL이 여러 개 생기는 것을 막습니다"*라고 정규형을 확정했습니다. `?q=react`와 `?q=react%20`는 **결과·헤더 요약·조건 바가 모두 같은 완전히 동일한 화면**인데 URL이 둘입니다. 기본값을 URL에서 빼는 것과 **같은 성격의 정규화**입니다 |
| **이미 반쯤 트림하고 있습니다** | `§3-8-4`는 공백만 남은 입력을 **빈 것으로 취급**하고, 구현도 `q`를 **쓸지 말지**는 트림값으로 판정합니다. 트림이 「키의 존재 여부」는 정하는데 「키의 값」은 안 정하는 상태입니다. 새 정책이 아니라 **이미 있는 규칙을 끝까지 적용**하는 것입니다 |
| **필터 계산에 영향 없음** | 매칭은 이미 `§3-2` 정규화(트림 포함)를 거치므로 **화면 결과가 달라지지 않습니다** |
| 🔴 **부수 결함 둘을 함께 없앱니다** | ①`?q=react` → `?q=react%20`는 `search`가 달라 **`push`가 되어 히스토리가 늘어납니다**(`§4-3`의 「같은 검색어 재실행 = `replace`」가 공백 하나에 무력화). ②`<ul>` key가 달라져 **결과가 동일한데 `listFadeUp`이 재생됩니다** — 이 PR이 없앤 원인 C와 같은 계열입니다 |

**「사용자가 친 공백이 사라진다」에 대해** — 사라지지 않습니다. **트림은 URL에 쓸 때만 적용하고 입력창 state는 건드리지 않습니다.** 커밋 후에도 입력창에는 사용자가 친 `react `가 그대로 남습니다. 공백이 없어지는 것은 새로고침·뒤로가기처럼 **입력창을 URL에서 새로 뜨는 경우**뿐이고, 그때는 `§3-8-5`에 따라 어차피 사본을 새로 뜨는 자리입니다.

### 4-4. 잘못된 파라미터 정규화

URL은 사용자가 직접 편집할 수 있고 오래된 링크도 들어옵니다. **절대 빈 화면이나 에러가 되면 안 됩니다.**

| 입력 | 처리 |
|---|---|
| 🔴 `?q=react%20` · `?q=%20react` (앞뒤 공백) | 트림해 `?q=react`로 `replace`. **전용 코드가 없습니다** — `buildPostListSearch`가 트림하므로 이 효과가 자동으로 처리합니다 (§4-2a) |
| `?category=study` (소문자) | 대소문자 무시 매칭 → `Study`로 정규화하고 URL을 `replace`로 고쳐 씁니다 |
| `?category=Foo` (없는 값) | 파라미터를 버리고 전체로. URL에서 키 제거 (`replace`) |
| `?sort=asc` / 알 수 없는 값 | `asc`는 `oldest`로 해석(관용). 그 외는 기본값으로, 키 제거 |
| `?page=0` · `?page=abc` · 음수 | `1`로 클램프, 키 제거 |
| `?page=99` (결과 3페이지) | **`totalPages`로 클램프**하고 URL을 `replace`. 빈 목록을 보여주지 않습니다 |
| 결과 0건인데 `?page=2` | `page=1`로 클램프한 뒤 빈 상태 표시 |
| `?q=` (빈 값) | 키 제거 |
| 알 수 없는 키 | **그대로 둡니다** (UTM 등 외부 추적 파라미터를 지우지 않습니다) |

**클램프는 렌더 이후가 아니라 파싱 단계에서** 합니다. `page=99`로 진입해 빈 목록이 한 프레임 그려진 뒤 고쳐지면 깜빡임이 보입니다.

**🔴 판정에 쓴 재료를 그대로 남깁니다** (이 판단은 자명하지 않습니다 — 다음 사람이 재론할 때 이 표를 쓰십시오)

| | |
|---|---|
| **반대 쪽 재료 ①** | 화면 아래에서 `검색` 버튼을 누른 사용자에게는 `§3-8-3`이 우려한 *"쳐도 아무 일이 안 일어난다"*와 **같은 모습**입니다 |

### 4-6. 🔴 검색 실행 시 문서 높이 — 스크롤 클램프 방지 (2026-08-02 신설)

#### 4-6-1. 무슨 일이 일어나는가

결과 수가 줄면 문서가 짧아집니다. 문서 높이가 `scrollY + innerHeight` 아래로 내려가면 **브라우저가 스크롤 위치를 강제로 끌어올립니다.** 코드에 `scrollTo`가 없어도 화면이 튑니다.

**QA 실측 (2026-08-02, 재현율 100%)**

| 입력 | 결과 | 문서 높이 | 이동 |
|---|---|---|---:|
| `r` → `re` (데스크톱) | 20 → 17건 | 2734 → 2394 | **−341px** |
| `react` → `reactq` (데스크톱) | 14 → 0건 | 2103 → 1030 | **−1,073px** |
| `react` → `reactq` (**모바일 390px**) | 14 → 0건 | 2432 → 1208 | **−1,224px** |
| `reactq` → `react` (한 글자 삭제) | 0 → 14건 | — | **+1,073px** |

- **커밋 기반으로 바뀌면 빈도가 「매 글자」에서 「실행 1회」로 줄지만, 사라지지는 않습니다.** 14 → 0건 실행 한 번에 1,073~1,224px는 그대로입니다

#### 4-6-2. 판정 — 「커밋 시 이동은 피드백이니 그대로 둔다」는 **반려**

검토했고, 아래 이유로 채택하지 않습니다.

| 반려 근거 | |
|---|---|
| **크기가 의미와 무관** | 클램프 이동량은 *결과가 얼마나 줄었는지*가 아니라 *사용자가 어디를 보고 있었는지*로 정해집니다. 같은 검색에 0px일 수도 1,224px일 수도 있습니다. **매번 크기가 다른 이동은 피드백이 아니라 잡음입니다** |
| **목적지가 무의미** | 클램프의 도착지는 "새 문서의 바닥"이지 결과의 시작점이 아닙니다. 사용자를 결과 어딘가 중간에 떨궈 놓습니다 |
| **신호가 이미 셋 있음** | 목록 헤더 요약(`§8-3`) · 「적용된 조건」 바(`§8-2`) · 재진입 애니메이션(`§9-1`). 넷째 신호가 필요하지 않고, 셋 다 **이동을 동반하지 않는** 신호입니다 |

**대신 채택**: 이동을 없애는 것이 아니라 **우리가 정한 목적지로 바꿉니다.** 아래 두 장치를 함께 씁니다.

#### 4-6-3. 장치 A — 커밋 시 명시 스크롤 (클램프 제거의 본체)

```

```

#### 4-6-3a. 🔴 `behavior`는 `'auto'` — `smooth`를 **쓰지 않습니다** (2026-08-02, frontend 보고 후 재판정)

원래 이 절은 `behavior`를 `§9-1` 9번(기본 `smooth`, `reduce`에서 `auto`)에 위임했습니다. **그 위임을 철회하고, 이 장치는 저감 설정과 무관하게 항상 즉시 이동합니다.**

**계기 — frontend 실측 (2026-08-02)**

- 카테고리 칩·페이지네이션을 실제 클릭해도 스크롤이 일어나지 않음(`scrollY` 1694 → 1694). 코드는 정상 — `navigationType='PUSH'`·key 변경·`scrollIntoView` 호출까지 전부 도달
- 원인은 그 Chrome 인스턴스에서 **`behavior:'smooth'`가 전면 무효**. `window.scrollTo({top:400, behavior:'smooth'})`도 무동작이고 **`prefers-reduced-motion`은 `false`**
- 같은 요소를 `behavior:'auto'`로 부르면 목적지(top 64px)로 **정확히 이동**

🔴 **즉, smooth가 죽으면 `§4-6-3`이 통째로 무효가 되고 브라우저 클램프만 남습니다 — 이 절이 없애려던 1,073~1,224px가 그대로 돌아옵니다.** 그리고 그 실패는 **조용합니다.**

**그러나 판정의 근거는 「환경 호환」이 아닙니다. 아래 넷 중 앞의 셋은 smooth가 정상인 브라우저에서도 성립합니다.**

| # | 근거 | |
|:--:|---|---|
| 1 | 🔴 **이 절 자신의 논리가 `auto`를 요구합니다** | `§4-6-3`은 「스크롤을 먼저 지시하면 클램프와 **하나의 이동**으로 보인다」는 근거로 채택됐습니다. 그 합성이 성립하려면 두 이동이 **같은 프레임**이어야 합니다. **클램프는 1프레임 즉시**이고 **smooth는 수백 ms 애니메이션**입니다 — 방향과 목적지는 같아도 **시간 특성이 달라 합성되지 않습니다.** smooth로 부르면 문서가 짧아지는 프레임에 클램프가 먼저 튀고(새 문서 바닥으로), 그 위를 우리 애니메이션이 뒤늦게 지나갑니다. 원문이 경고한 **「두 번 움직임」이 순서가 아니라 `behavior` 때문에 발생**합니다. `auto`만이 클램프와 동시에 일어나 실제로 하나의 이동이 됩니다 |

#### 4-6-3b. 🔴 목적지에 **도달할 수 없을 때** — `maxScroll` 착지는 결함이 아닙니다 (2026-08-02 신설)

#### 4-6-4. 장치 B — 결과 슬롯 최소 높이 예약

**「결과 슬롯」의 정의**: 목록 헤더 **아래 전부** — `<ul>`(또는 빈 상태) **+ 페이지네이션**을 감싸는 래퍼 하나.

- 페이지네이션을 래퍼 **안에** 넣는 이유: 0건이면 페이저가 통째로 사라집니다(`§7-3`). 페이저를 밖에 두면 그 소실분(약 72px)을 예약이 못 잡습니다

| **왜 1,073px 전량이 아닌가** | 전량 흡수는 0건 화면에 화면 하나만큼의 공백을 남겨 **그 자체가 고장으로 보입니다.** 클램프 제거는 장치 A가 담당하므로 예약이 전량을 떠맡을 이유가 없습니다 |
| **왜 뷰포트 비례가 아닌 고정값인가** | `100vh`·`100dvh`·`innerHeight` 기반 값은 **iOS Safari의 동적 툴바가 오르내릴 때마다 슬롯 높이가 변합니다.** 스크롤만 해도 레이아웃이 흔들립니다. 고정 px는 그런 결합이 없고 QA가 한 값으로 검증할 수 있습니다 |
| **모바일 차등** | 🔴 **두지 않습니다.** 모바일 이동량이 더 크지만(1,224px) 그건 장치 A가 해결합니다. 예약값을 폭마다 다르게 두면 "왜 이 값인가"를 두 번 설명해야 하고, 480px는 두 폭 모두에서 4~5행 상당이라 체감이 같습니다 |

**🔴 5건 경계 — 480px 유지, 표현만 정정** (2026-08-02, QA 지적 후 판정)

QA 실측: 데스크톱 5편 결과의 슬롯 **자연 높이 485px** — 하한 480px과 **5px 차**. 제목이 전부 1행인 5건이 나오면 예약이 발동합니다. 원래 적은 **「5건 이상에서는 발동하지 않습니다」는 보장이 아니었고, 모바일에서는 이미 거짓**이었습니다(모바일 5행 약 435px < 480px).

**그럼에도 480px을 유지합니다. `--list-floor` 값 변경은 필요 없습니다.**

| | |
|---|---|
| **틀린 것은 값이 아니라 표현** | 예약은 켜짐/꺼짐이 아니라 **연속**입니다. 실제로 보이는 여백 = `max(0, 480 − 자연높이)`. 경계에 가까울수록 여백이 0에 수렴합니다. 데스크톱 5건은 **5px** — 지각되지 않습니다. 모바일 5건은 약 **45px**로 반 행 남짓이라 "구멍"이 아니라 슬롯 아래 여유로 읽힙니다. 발동 여부가 아니라 **여백의 크기**가 판정 대상입니다 |
| **값을 내리면 잃는 것** | 하한을 4행 상당(약 390px)까지 내리면 경계는 확실히 4건 아래로 내려가지만, 0건 흡수량이 160px → 70px로 **절반 이하**가 됩니다. 하한의 본래 목적(빈 상태 교체 시 문서 높이 변화 완충)을 깎아 5px짜리 여백을 없애는 거래는 **손해**입니다 |
| **재작업 비용** | 값 변경은 `frontend` 재작업 + V1~V6 전량 재측정을 부릅니다. 5px에 대해 치를 비용이 아닙니다 |

**재검토 트리거** — 아래에 해당하면 그때 값을 다시 봅니다. 그전에는 480px 고정입니다.

- 어느 폭에서든 **5건 결과의 여백이 60px(약 반 행)을 넘길 때**
- 행 높이가 구조적으로 바뀔 때(썸네일 도입·행 패딩 변경 등) — 하한은 **행 높이 파생값이 아니라 빈 상태 높이(약 320px) 기준으로 다시** 정합니다

**정렬 기준**

| 항목 | 확정 |
|---|---|
| 슬롯 내부 정렬 | 🔴 **상단 정렬.** 남는 예약분은 **콘텐츠 아래**로 흘립니다 |
| **세로 중앙 정렬** | 🔴 **금지.** 중앙 정렬하면 빈 상태 메시지의 세로 위치가 슬롯 높이에 따라 달라져, **같은 조건인데 결과 수에 따라 메시지가 다른 자리에** 뜹니다 |
| 가로 정렬 | `§8-4` 그대로 **가로 중앙** 유지 |
| 빈 상태 상단 패딩 | `--space-16`(64px) 유지. 이 패딩이 목록 헤더와 메시지 사이 간격을 결정하고, 그 간격은 예약량과 무관하게 **항상 같아야** 합니다 |

**빈 상태와 리스트가 컨테이너 높이를 공유하는가** → 🔴 **하한만 공유합니다. 상한은 공유하지 않습니다.** 래퍼가 `min-height: var(--list-floor)`를 갖고, 그 안에서 `<ul>`과 빈 상태가 교체됩니다. 「검색 세션 동안 직전 높이를 유지」하는 방식은 **반려** — 14건 뒤의 0건과 처음부터의 0건이 다르게 보이고(같은 URL·같은 결과인데 화면이 다름), 새로고침하면 또 달라집니다. **화면은 URL만 보고 결정돼야 합니다**(`§4-1`).

#### 4-6-5. 구현 함정

- 🔴 슬롯 하한을 **스크롤 위치에 따라 동적으로 키우지 마십시오.** 아래로 스크롤할수록 문서가 따라 늘어나 **문서 끝에 영영 도달하지 못합니다**
- 🔴 전역에 `overflow-anchor: none`을 걸지 마십시오. 브라우저의 기본 스크롤 앵커링이 「적용된 조건」 바처럼 **뷰포트 위쪽에 삽입되는 요소**를 보정합니다
- 슬롯 하한은 **상시 적용**입니다. 검색 중에만 켜면 켜고 끄는 시점마다 높이가 변합니다

#### 4-6-6. 🔴 원칙 — **착지는 기능, 애니메이션은 장식** (2026-08-02 신설)

> **애니메이션이 한 프레임도 돌지 않아도 스크롤은 반드시 목적지에 착지해야 합니다.**
> 장식이 실패해서 기능이 사라지는 구조를 이 화면에 두지 않습니다.

이 원칙은 `§4-6-3a`의 상위 규칙이고, 이 문서 전체와 이후 STEP의 스크롤 지시에 적용됩니다.

| 규칙 | |
|---|---|
| **R1** | **착지를 애니메이션 인자에 의존시키지 마십시오.** `behavior:'smooth'`는 브라우저·플래그·정책·임베디드 웹뷰에서 **조용히 무시될 수 있는 요청**입니다. 착지가 그 인자의 성공에 달려 있으면, 인자가 무시되는 순간 기능이 통째로 사라집니다 |
| **R2** | 어떤 화면에서 `smooth`를 쓴다면, **그 이동이 실패해도 화면이 정상**이어야 합니다(목차 점프처럼 사용자가 스스로 다시 이동할 수 있는 보조 이동). **레이아웃 결함을 막는 이동에는 `smooth`를 쓸 수 없습니다** — 실패가 곧 결함의 부활입니다 |
| **R3** | 🔴 **smooth 지원 여부를 런타임 탐지해 분기하지 마십시오.** 아래 「탐지를 반려하는 이유」 |

**「폴백을 넣을 것인가」 → 🔴 넣지 않습니다. 의존 자체를 제거합니다.**

`§4-6-3a`가 `behavior:'auto'`로 확정했으므로 이 경로에는 **폴백을 붙일 대상이 없습니다.** 폴백은 「smooth를 쓰되 실패하면 auto로」라는 구조를 전제하는데, 그 구조가 필요 없습니다.

**탐지를 반려하는 이유** (다음 사람이 "감지해서 분기하자"로 되돌리지 않도록)

| | |
|---|---|
| `prefers-reduced-motion`으로는 **못 잡습니다** | 이번 케이스에서 값이 `false`였습니다. 이 미디어쿼리는 *사용자 선호*를 알려줄 뿐 **엔진이 smooth를 실행하는지**는 말해 주지 않습니다 |
| 기능 탐지가 **없습니다** | `'scrollBehavior' in document.documentElement.style`은 **CSS 속성 파싱 지원** 여부일 뿐이라, smooth가 플래그·정책으로 꺼진 환경에서도 `true`를 돌려줍니다 |
| 실측 탐지는 **부작용이 큽니다** | 실제로 판정하려면 시험 스크롤을 걸고 다음 프레임에 위치를 재야 하는데, **그 시험 자체가 화면을 움직이고**, 판정이 나오기까지 최소 1~2프레임이 필요합니다. 클램프는 그 사이에 이미 일어납니다 |
| 분기는 **경로를 둘로 늘립니다** | QA가 V1~V6을 두 경로에서 각각 재야 하고, 둘 중 하나는 재현이 어려운 환경입니다. 분기 없는 `auto`는 **검증 대상이 하나**입니다 |

**되돌림 방지** — 이 판정을 뒤집으려면 `§4-6-3a` 근거 1~3(시간 특성 불일치 · 1,200px 애니메이션 · `fadeUp` 신호 삼킴)을 각각 반박해야 합니다. 「최근 브라우저에서는 smooth가 잘 된다」는 근거 4만 건드리므로 **되돌림 사유가 되지 않습니다.** 검증은 `§6-4` **V6**가 지킵니다.

**frontend 조치** (구현 변경 — 이 문서가 요청합니다)

| 파일 | 조치 |
|---|---|
| `src/routes/Posts/Posts.tsx` | 🔴 스크롤 효과의 `behavior`를 **`'auto'` 고정**으로. 현재 `prefersReducedMotion() ? 'auto' : 'smooth'` |
| 〃 | 🟡 `prefersReducedMotion()` 지역 헬퍼가 이 효과 외에 쓰이지 않으면 **함께 제거**. 남겨 두면 다음 사람이 "왜 안 쓰지"로 되돌립니다 |
| 〃 | 🔴 이 효과 옆에 **`auto`인 이유를 §4-6-3a 참조로 주석**에 남길 것. 근거 없는 `'auto'`는 리팩터링 때 `smooth`로 "개선"됩니다 |
| `Posts.module.css`·전역 | 🟢 변경 없음. 전역 CSS는 이미 `scroll-behavior` 기본이 `auto`이고 저감 모드에만 `auto !important` 그물이 있습니다. **`html { scroll-behavior: smooth }`를 새로 추가하지 마십시오** — CSS로 들어오면 JS 인자와 무관하게 이 장치가 다시 애니메이션이 됩니다 |

#### 🔴 V6 재현법 — smooth 무효 환경 만들기 (2026-08-02 신설)

frontend가 만난 현상(자동화 Chrome에서 `behavior:'smooth'`가 **조용히 무동작**, `prefers-reduced-motion`은 `false`)을 **어느 브라우저에서든** 재현합니다. 페이지 스크립트보다 **먼저** 주입해야 합니다(Playwright `addInitScript`, 수동이면 콘솔에서 실행 후 조작).

```js
/* smooth 요청만 조용히 무시 — 무효 환경 에뮬레이션 */
const _sIV = Element.prototype.scrollIntoView;
Element.prototype.scrollIntoView = function (opt) {
    if (opt && typeof opt === 'object' && opt.behavior === 'smooth') return;   // no-op
    return _sIV.apply(this, arguments);
};
const _sTo = window.scrollTo;
window.scrollTo = function (opt) {
    if (opt && typeof opt === 'object' && opt.behavior === 'smooth') return;   // no-op
    return _sTo.apply(window, arguments);
};
/* CSS 경로도 함께 차단 */
document.documentElement.style.setProperty('scroll-behavior', 'auto', 'important');
```

#### 🔴 V1-주 — `scrollY`를 V1의 측정값으로 쓰지 마십시오 (2026-08-02, QA 반증 후 재작성)

원래 V1은 **「타이핑 중 `window.scrollY` 변화 0px」**이었습니다. **이 기준은 글자 그대로는 만족 불가능합니다.** 명세 오류이며, 아래를 읽지 않고 되돌리지 마십시오.

**구조적 이유**

- 인라인 입력창은 **문서 최상단**에 있습니다. V1의 시작 조건인 `scrollY ≈ maxScroll/2`에서는 **입력창과 캐럿이 화면 밖**입니다
- 포커스된 입력에 **실제 키 이벤트**가 들어오면 브라우저는 캐럿을 화면 안으로 되돌립니다. 사양상의 동작이고 끌 수 없습니다
- 따라서 첫 타건에서 데스크톱 **−696px** · 모바일 **−954px**이 **반드시** 발생합니다. 이후 5글자 동안은 0px입니다(캐럿이 이미 보이므로)

**이것이 클램프가 아니라는 증거 — QA 통제 실험 (2026-08-02)**

| 조작 | Δ `scrollY` | `docH` | 슬롯 문서좌표 | rows | URL |
|---|---:|---|---|:--:|---|
| `ArrowRight` (포커스 O, **값 불변**) | 0px | 불변 | 불변 | 불변 | 불변 |

레이아웃 값은 **하나도 변하지 않았고** V3는 한 번도 거짓이 아니었습니다. 🔴 **`scrollY`는 「레이아웃이 변했는가」와 「캐럿이 복귀했는가」를 구분하지 못합니다.** 원 기준은 후자를 전자로 오독합니다. `docH`·슬롯 문서좌표·rows·URL은 그 구분이 됩니다 — 원 버그(`docH` 2734 → 2394)는 이 넷에 **전부** 걸립니다.

**캐럿 복귀 자체는 결함인가** → **아닙니다.** 첫 타건 1회뿐이고, 화면 밖 입력창에 타이핑하는 상황에서 입력 지점을 보여 주는 것은 올바른 동작입니다. 이 이동을 없애려 하지 마십시오(입력창을 sticky로 만들거나 `preventScroll`을 쓰는 대응은 **반려** — 원인이 결함이 아닙니다).

**🔴 측정 방법이 결과를 바꿉니다 — 이번에 기준이 무력화된 진짜 원인**

| 측정 방법 | 타이핑 중 Δ `scrollY` | 잡히는 것 |
|---|---:|---|
| **실제 키 이벤트** (Playwright `type`/`press`, 사람 손) | −696 / −954px | 사용자가 겪는 전부. 🔴 **정본** |
| `input.value = …` + `dispatchEvent` (포커스 우회) | **0px** | 레이아웃 변화만. **캐럿 복귀가 빠져 사용자 경험과 다름** |

원 V1을 「0px」로 적을 수 있었던 것은 **값 주입 방식으로만 재봤기 때문**입니다. V1은 **반드시 실제 키 이벤트로** 측정하고, 값 주입은 보조 대조군으로만 씁니다. 두 방법의 수치가 갈리면 그것은 결함 신호가 아니라 **캐럿 복귀의 존재**를 뜻합니다 — 판정은 항상 `docH`·슬롯 문서좌표·rows·URL로 합니다.

> 🔴 **합격 기준과 구현을 같은 커밋에 담지 마십시오.** 이 오류가 걸러지지 않은 이유는 V1~V5와 그 구현이 한 커밋에 있어 **명세를 독립적 오라클로 볼 수 없었기** 때문입니다. 검증 기준 변경은 구현 커밋과 분리하고, 기준을 쓴 주체와 재는 주체를 나눕니다.

| 비활성 페이지 | 배경 `--color-bg-raised`, 글자 `--color-text-secondary`, 테두리 `--color-border-default` |
| 이전/다음 비활성 | `aria-disabled="true"` + `pointer-events: none` + `opacity: .45`. **`<a>`를 남기되 `href`를 제거** |
| `aria-label` | `이전 페이지` / `다음 페이지` / `3페이지로 이동` (WRITING_GUIDE §6.9) |
| `←` `→` `<<` `>>` | `aria-hidden="true"` |
| `1 / 3` 표시 | 목록 헤더 우측과 페이저 우측 **두 곳** (시안 유지) |
| 결과 1페이지 이하 | 페이저 전체를 **렌더하지 않습니다** |
| 결과 0건 | 페이저 없음 (빈 상태만) |

**번호 생략 규칙 (지금은 불필요, 계약만 남깁니다)**: 전체 페이지가 **8을 넘으면** `1 … 4 [5] 6 … 12` 형태로 축약합니다. 현재 최대 3페이지라 발동하지 않습니다. 시안은 `Array.from({length: totalPages})`로 전부 렌더하므로 글이 늘면 페이저가 가로로 넘칩니다.

**`Pagination.tsx` 수정 사항**
- `<button>` + `navigate()` → `<a href>` (§5-2)
- `urlPath` 하나가 아니라 **현재 쿼리를 보존**하고 `page`만 바꿔야 합니다. 현재 코드는 `${urlPath}?page=N`으로 **`q`·`category`·`sort`를 전부 날립니다**
- `<<` `>>`(첫/마지막) 버튼은 3페이지에서 잉여 → 제거. 8페이지 초과 시 부활

### 9-2. 스켈레톤 — 🔴 가장 틀리기 쉬운 곳

```css
/* 기본 */
.skeleton {
  background: linear-gradient(90deg,
    var(--color-skeleton-base) 0%,
    var(--color-skeleton-sheen) 50%,
    var(--color-skeleton-base) 100%);
  background-size: 320px 100%;      /* keyframes 이동폭과 반드시 일치 */
  animation: shimmer 1.4s linear infinite;
}

@media (prefers-reduced-motion: reduce) {
  .skeleton {
    animation: none;
    background: var(--color-skeleton-base);   /* ← 그라데이션을 통째로 교체 */
    background-size: auto;
  }
}
```

**`animation: none`만 쓰면 안 됩니다.** 그라데이션이 `background-position: -320px`에서 얼어붙어, 막대마다 밝은 띠가 엉뚱한 위치에 멈춘 상태로 남습니다. 시안의 수동 토글이 정확히 이 결과를 만듭니다.

> **시안 버그**: `background-size: 520px 100%`인데 `@keyframes shimmer`는 `-320px → 320px`를 움직입니다. 이동폭과 그라데이션 폭이 어긋나 sheen이 화면 밖에 있는 구간이 생깁니다. **520 → 320으로 통일**하십시오.

### 9-3. 색·배경 전환을 유지하는 이유

`prefers-reduced-motion`은 **전정 자극(vestibular)** — 위치·크기·회전 변화를 겨냥합니다(WCAG 2.3.3 Animation from Interactions). 색·투명도 전환 160ms는 여기 해당하지 않으며, 제거하면 호버 피드백이 뚝뚝 끊겨 **오히려 상태 파악이 어려워집니다.**

**금지**: 전역 `*, *::before, *::after { animation: none !important; transition: none !important }` 카펫 폭격. 위 스켈레톤 문제가 정확히 이 방식의 결과이고, 필요한 피드백까지 같이 죽습니다. **모션별로 개별 처리하십시오.**

### 9-4. 모션이 사라진 자리를 무엇이 메우는가 — 🔴 필수

필터 전환의 재진입 애니메이션은 "목록이 바뀌었다"는 **유일한 시각 신호**입니다. 저감 모드에서는 그 신호가 사라지고, 스크린리더 사용자는 애초에 받은 적이 없습니다.

**대체 장치**: 목록 헤더의 결과 수를 `aria-live` 영역으로 만듭니다.

```
<div aria-live="polite" aria-atomic="true">
  react · 14편 일치 · 전체 41편 중
</div>
```

- `➜` 등 장식 기호는 이 영역 안에서 `aria-hidden` (WRITING_GUIDE §7.4 — *"`aria-live`에 장식 기호를 넣지 않음"*)
- `polite` (`assertive` 아님). 낭독이 입력을 끊으면 안 됩니다
- ~~타이핑마다 발화되지 않도록 **URL 반영과 같은 250ms 디바운스**를 겁니다~~
  → 🔴 **폐기 (2026-08-02).** **디바운스가 필요 없습니다.** 이 영역을 URL의 `q`에서 렌더하면 값이 커밋에서만 바뀌므로 **실행당 1회** 발화합니다(`§3-8-1`). 디바운스는 라이브 필터가 만든 문제를 덮으려던 장치였고, 그 문제가 없어졌습니다
  - 부수 이득: 사용자가 Enter를 누른 **직후** 결과 수가 낭독됩니다. 디바운스 방식은 타이핑을 멈추고 250ms를 기다려야 발화해, **실행과 안내 사이에 설명할 수 없는 지연**이 있었습니다
- 로딩 중에는 컨테이너 `aria-busy="true"`로 중간 상태 낭독을 억제
