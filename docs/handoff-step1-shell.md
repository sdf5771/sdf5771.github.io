| 픽셀 서체는 **11의 정수배에서만 선명** | Galmuri11이 11px 비트맵 그리드 (Part II-F3) |

**11 < 12** 이므로 한글 + 픽셀의 최소 크기는 **22px**입니다. 메타·라벨에 22px은 쓸 수 없으므로 결론은 하나입니다.

**적용표**

| 서체 | 허용 크기 | 허용 문자 |
|---|---|---|
| `Galmuri11` (디스플레이) | 22 / 33 / 44 / 55 / 66px | **한글 포함 전부** |
| `Galmuri11` | 11px | **라틴·숫자·기호만** |
| `GalmuriMono11` (모노) | **11px 고정** | **라틴·숫자·기호만** |
| `Pretendard` | 12px 이상 자유 | 전부 |

- 22px 미만에서 픽셀 느낌이 필요하면 **크기를 22px로 올리거나, 픽셀을 포기**하는 두 선택지뿐입니다. 중간은 없습니다
- `Galmuri14`(14px 그리드)를 추가하면 14px 한글 픽셀이 가능하지만, **채택하지 않습니다** — 원본 551.6 KB가 추가되고, 11px 그리드와 도트 밀도가 달라 한 화면에서 두 격자가 충돌합니다
- 이 규칙은 **§4-3의 서브셋으로 기술적으로 강제**됩니다 (모노에서 한글 글리프 제거 → 한글은 자동으로 Pretendard 폴백)

#### 4-2a. 🔴 추가 제외 블록 6종 — 전부 제거 (2026-08-01 판정)

"한자·카나 제거"만 적용하면 원본에 아래 블록들이 남아 **226.2 KB**가 됩니다. **6개 모두 제거하세요.**

| 블록 | 범위 | 판정 | 사유 |
|---|---|:---:|---|
| 점자 | `U+2800–28FF` (256자) | ❌ 제거 | 사용처 없음 |
| **괘선(Box Drawing)** | `U+2500–257F` | ❌ **제거** | 아래 별도 설명 |
| 제어그림 | `U+2400–243F` | ❌ 제거 | `␣` `␤` 등. 사용처 없음 |
| 사용자영역(PUA) | `U+E000–F8FF` | ❌ 제거 | 비표준 사설 글리프. 참조하면 안 되는 영역 |
| 원문자·단위 | `U+3200–33FF` | ❌ 제거 | `㈜` `㎡` `㎏` 등. 본문은 Pretendard이므로 픽셀 서체에 불필요 |
| 라틴확장추가 | `U+1E00–1EFF` | ❌ 제거 | 베트남어·발음기호. 한국어+영어 사이트에 불필요 |

**괘선(`─ │ ┌ ┐`)을 빼는 이유 — 디자인에서 쓸 계획이 없습니다.**

1. **테두리·구분선은 CSS 보더로 그립니다.** `--color-border-subtle/default/strong/interactive` 4단계가 이미 있고 **대비 실측을 거친 값**입니다. 문자 그래픽으로 그린 선은 토큰화도 대비 검증도 불가능합니다.
2. **터미널 창 크롬을 이미 반려했습니다** (design.md Part II-C5 — 신호등 3개·창 테두리 제외). 괘선 테두리는 그 결정을 뒷문으로 되돌리는 셈입니다.
3. **크기가 맞지 않습니다.** 모노는 §3-3a에 따라 **11px 고정**이라 괘선이 너무 작고, 디스플레이는 22px 이상이라 너무 큽니다. 중간이 없습니다.
4. **정렬이 깨집니다.** 문자 괘선은 진짜 고정폭 + 정확한 `line-height`에서만 이어지는데, 우리 모노는 짧은 인라인 문자열용이지 여러 줄 아트용이 아닙니다.
5. 스크린리더가 의미 없는 문자열로 읽어 어차피 `aria-hidden`이 필요합니다.

> **규칙: 테두리·구분선·박스는 CSS 보더 토큰으로 그립니다. 문자 그래픽으로 그리지 않습니다.**
> 나중에 정말 필요해지면 `scripts/subset-galmuri.py`에서 해당 블록만 되살리면 됩니다 — 되돌리기 쉬운 결정입니다.

⚠️ 부작용: 이 블록들의 문자가 제목·헤딩에 들어가면 Pretendard로 폴백돼 한 단어 안에서 서체가 갈립니다. 대상이 점자·괘선·PUA·베트남어라 실사용 위험은 사실상 0입니다.

> **용량 이력 (정리)**: 블랙리스트 방식 226.2 → 6블록 제거 198.2 → **화이트리스트 전환 169.3 KiB(최종)**.
> 제가 처음 잰 169.3 KiB가 결과적으로 맞았습니다 — 그 측정이 이미 화이트리스트 방식이었기 때문입니다. 중간에 제시한 191.5 KiB는 블랙리스트 전제의 추정치였으므로 **폐기**합니다.
> 예산 ≤1MB의 **17%**로, 여유가 충분합니다.

**모노에서 한글을 빼는 것이 핵심입니다 (2026-08-01 변경).**

### 4-3a. 🔴 서브셋 방식 — 화이트리스트로 전환 (2026-08-01 판정)

**판정: 화이트리스트(유지 목록) 방식으로 전환. 단 빌드타임 단언을 함께 넣으세요.**

**먼저 — 6.7 KiB는 문제가 아닙니다.** 현재 198.2 KiB는 예산(≤1MB)의 **19.8%**이고, 목표 미달분은 예산의 **0.67%**입니다. 용량만 보면 그냥 두어도 됩니다. **용량을 이유로 전환하는 것이 아닙니다.**

전환하는 진짜 이유는 둘입니다.

1. **결정성.** 블랙리스트는 "아는 나쁜 것만 뺀다"이므로, 상류 Galmuri 패키지가 다음 버전에서 글리프를 추가하면 **우리 번들이 조용히 커집니다.** 화이트리스트는 그럴 수 없습니다.
2. **규칙의 코드화.** 유지 목록이 §4-7("서브셋 cmap에 있는 문자만 쓴다")을 빌드에 박아 넣는 역할을 합니다. 문서가 아니라 빌드가 규칙을 지킵니다.

**⚠️ 전환의 위험과 그 해소** — frontend 경고가 정확합니다. 유지 목록에서 빠뜨린 기호는 **조용히 사라져 폴백 서체로 렌더**됩니다. 이건 방금 겪은 `➜`·`⌕` 사고와 **증상이 같고, 원인이 우리 쪽이라 더 나쁩니다.**

→ **빌드타임 단언을 필수로 넣으세요.** 서브셋 생성 직후 두 파일의 cmap에 아래 인벤토리가 전부 있는지 검사하고, 하나라도 없으면 **빌드를 실패시킵니다.** 이러면 화이트리스트의 위험이 "조용한 시각 버그"에서 "빌드 에러"로 바뀝니다.

```python
REQUIRED = '▸×●○→←↑↗★·…–☰⌘'   # §4-7 인벤토리와 동기화할 것
for path in (DISPLAY_OUT, MONO_OUT):
    cmap = TTFont(path).getBestCmap()
    missing = [c for c in REQUIRED if ord(c) not in cmap]
    if missing:
        raise SystemExit(f'서브셋 누락: {path} → {missing}')
```

#### 4-3b. 단언 범위 확장 (2026-08-01 판정)

현재 `verify-font-glyphs.mjs`는 **장식 기호 14자만** 검사합니다. 세 줄을 더 넣어 실제 위험을 덮으세요.

| # | 단언 | 잡는 사고 |
|:--:|---|---|
| 1 | 장식 기호 14자가 **두 파일 모두**에 존재 | (현행 유지) 유지 목록 누락 |
| 2 | **디스플레이 서브셋의 한글 음절이 정확히 11,172자** | 누군가 디스플레이 범위를 좁혀 **한글 제목이 폴백**되는 파국적 사고 |
| 3 | **모노 서브셋의 한글 음절이 정확히 0자** | 누군가 "한글이 없네"라며 모노에 한글을 추가해 **§3-3a 규칙이 조용히 죽는 것** |

```js

assert(hangul(displayCmap) === 11172, '디스플레이 한글 누락');
assert(hangul(monoCmap)    === 0,     '모노에 한글이 들어갔습니다 — §3-3a 위반');
```

**QA가 발견한 "mono에 `태·그·글·개`가 없다"는 결함이 아니라 설계대로입니다.** 모노는 §4-3에 따라 한글이 없어야 하고, 해당 문자열은 전부 `sr-only`라 시각 영향이 0이며, 보이는 자리에 들어왔다면 §4-4의 Pretendard 폴백이 받습니다. **3번 단언은 그 설계가 유지되는지를 지키는 장치**입니다.

> **보이는 한글의 서체 오용은 폰트 단언으로 잡을 수 없습니다** — 서브셋은 올바르고 문제는 *사용처*이기 때문입니다. 그건 §3-3a 규칙과 코드 리뷰가 맡습니다. 단언은 **서브셋이 계약대로인지**만 검사하면 충분합니다.

### 4-4. `@font-face` 및 폰트 토큰

```css
@font-face {
  font-family: 'Galmuri11';
  src: url('/fonts/Galmuri11-subset.woff2') format('woff2');
  font-weight: 400; font-style: normal; font-display: swap;
}
@font-face {
  font-family: 'GalmuriMono11';
  src: url('/fonts/GalmuriMono11-subset.woff2') format('woff2');
  font-weight: 400; font-style: normal; font-display: swap;
}

:root {
  --font-display: 'Galmuri11', 'Pretendard', sans-serif;
  --font-mono:    'GalmuriMono11', 'Pretendard', ui-monospace, monospace;
  --font-body:    'Pretendard', -apple-system, system-ui, sans-serif;
}
```

> `--font-mono`의 2순위가 `IBM Plex Mono`가 아니라 **`Pretendard`** 인 것은 의도적입니다. IBM Plex Mono는 이 프로젝트에 없고, 모노 서브셋에 한글이 없으므로 한글이 들어오면 **Pretendard로 폴백**되어야 합니다. 시스템 모노(`ui-monospace`)로 떨어지면 OS마다 한글 서체가 달라져 예측이 불가능합니다.

- ✅ **Pixelify Sans 폴백은 불필요합니다.** Galmuri11·GalmuriMono11 모두 한글 11,172자를 완전히 포함하는 것을 직접 확인했습니다. 시안 주석의 주장이 사실입니다.
- Pretendard는 이미 `src/assets/fonts/`에 로컬로 있습니다. **CDN(`cdn.jsdelivr.net/gh/orioncactus/pretendard`)을 추가하지 마세요.**
- 히어로 워드마크가 LCP 요소가 될 가능성이 높으므로 `Galmuri11-subset.woff2`만 `<link rel="preload">` 하세요. 나머지는 preload 하지 않습니다(대역폭 경합).

### 4-5. 픽셀 렌더링 규칙

## 5. 테마 전환

### 5-1. 3단계 상태

```
localStorage["theme"] = "system" | "light" | "dark"     ← 사용자 선택
              ↓ 해석
<html data-theme="light" | "dark">                      ← 실제 적용값만
```

- 기본값 **`system`**. 토글은 `system → light → dark → system` 순환
- `system`일 때 `prefers-color-scheme` 변화를 **런타임에 구독**해야 합니다 (`matchMedia('(prefers-color-scheme: dark)').addEventListener('change', …)`). OS 테마가 바뀌면 즉시 따라가야 합니다

### 5-2. 🔴 FOUC 방지 — 인라인 블로킹 스크립트 필수

`index.html`의 `<head>` 안, **모든 CSS보다 먼저**:

```html
<meta name="color-scheme" content="dark light" />
<script>
  (function () {
    try {
      var s = localStorage.getItem('theme') || 'system';
      var d = s === 'dark' || (s === 'system' &&
        window.matchMedia('(prefers-color-scheme: dark)').matches);
      document.documentElement.setAttribute('data-theme', d ? 'dark' : 'light');
    } catch (e) {
      document.documentElement.setAttribute('data-theme', 'dark');
    }
  })();
</script>
```

React 마운트 전에 `data-theme`이 결정돼야 합니다. 없으면 다크 사용자가 매 진입마다 흰 화면 섬광을 봅니다. GitHub Pages 정적 환경에서도 이 방식이 그대로 동작합니다.

### 5-3. `color-scheme` 병행

```css
:root { color-scheme: dark; }
[data-theme="light"] { color-scheme: light; }
```

빠뜨리면 다크 화면에 **흰 스크롤바**가 남고, `<input>` 자동완성 배경이 밝게 뜹니다.

### 5-4. 전환 순간 트랜지션 차단

색에 `transition`이 걸려 있으면 토글 시 화면 전체가 훑히듯 바뀌어 어지럽습니다.

## 5-6. 🔴 전역 저감 모션 규칙 (2026-08-01 판정)

### 확정안 — `transition-duration` 한 줄을 삭제합니다

```css
/* src/global.css */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .01ms !important;
    animation-iteration-count: 1 !important;
    scroll-behavior: auto !important;
  }
}
```

**변경은 `transition-duration: .01ms !important;` 삭제 하나뿐입니다.**

### 왜 `transition`을 빼는가

**① `prefers-reduced-motion`은 색 전환을 대상으로 하지 않습니다.**
이 설정은 **전정기관 자극**(vestibular) — 움직임이 유발하는 어지럼·구역 — 을 막기 위한 것입니다. WCAG 2.3.3도 *motion animation*이 대상입니다. **배경색·글자색·테두리색 전환은 아무것도 움직이지 않으므로 억제할 이유가 없습니다.** 오히려 호버 피드백을 즉시 전환으로 만들어 인터페이스를 딱딱하게 만듭니다.

**② `transition-duration: 0`은 `transform`에 대해 애초에 효과가 없습니다.**
`translateY(-3px)` 호버에 지속시간을 0으로 줘도 **요소는 여전히 3px 점프합니다.** 즉시 움직이는 것도 움직이는 것입니다. 이 규칙은 **막아야 할 것은 못 막고**(transform), **막지 말아야 할 것만 막고 있었습니다**(색). 방향이 양쪽 다 틀렸습니다.

**③ 컴포넌트 규칙을 전부 이깁니다.**
`!important`가 붙어 있어 컴포넌트의 저감 사양이 무력화됩니다. QA가 실측한 피해 8건(행 호버 배경·제목색, 카테고리 칩, 정렬 세그먼트, 조건 해제 링크, 페이지네이션, 빈 상태 버튼, 검색 포커스 테두리)이 전부 이 한 줄 때문이며, `PostRow`의 120ms 페이드 저감 사양(`:311`)까지 함께 죽습니다.

### 왜 나머지 셋은 남기는가

| 선언 | 판정 |
|---|---|
| `animation-duration` / `-iteration-count` | ✅ **유지.** 키프레임 애니메이션은 대부분 실제 움직임이고, **무한 반복(커서 blink·bob)을 잊고 남겨두는 것이 최악의 실패**입니다. 그물이 필요한 자리입니다 |
| `scroll-behavior: auto` | ✅ **유지, `!important` 필수.** 부드러운 스크롤은 **뷰포트 전체가 움직이는 전형적 전정 자극**입니다. STEP 3 지적대로 `scroll-behavior: smooth`는 `!important`로 덮지 않으면 앵커 이동이 계속 부드럽게 동작합니다. 전역이 실제로 필요한 유일한 케이스입니다 |

> `animation: none`은 `animation-name`을 바꾸므로 이 규칙과 충돌하지 않습니다. 컴포넌트의 `animation: none` 저감 사양은 그대로 동작합니다.

### 컴포넌트가 지켜야 할 일반 규칙 (STEP 2·3·6·7 전부 적용)

> ## **저감 모션에서 `transform`은 값을 지우고, 색·투명도 전환은 그대로 둔다.**
> ## **지속시간을 0으로 만드는 것은 해결이 아닙니다 — 즉시 이동도 이동입니다.**

```css
/* ✅ 올바른 컴포넌트 저감 사양 */
@media (prefers-reduced-motion: reduce) {
  .card:hover      { transform: none; }        /* 값을 제거 */
  .row__bar        { transform: scaleY(1); }   /* 최종 상태로 고정 */
  .row__arrow      { transition-duration: 0s; }/* opacity만 쓰는 경우엔 선택 */
}
/* ❌ 하지 말 것 */
.card { transition-duration: .01ms; }          /* transform이 여전히 점프함 */
```

**적용 대상 판정표**

| 전환 속성 | 저감 모션에서 | 이유 |
|---|---|---|
| `transform` (translate·scale·rotate) | **값 제거 또는 최종 상태 고정** | 실제 움직임 |
| `background-color` · `color` · `border-color` | **그대로 유지** | 움직임 아님 |
| `opacity` | **유지 가능.** 필요하면 지속시간만 단축 | 전정 자극 없음 — 오히려 모션의 권장 대체재 |
| `width`/`height`/`top`/`left` 등 레이아웃 | **값 제거** | 주변까지 밀어내는 움직임 |
| 스크롤 연동 진행바 | **유지** | 기능적 피드백이고 사용자 스크롤에 종속 |

**그물이 사라지는 자리는 없습니다.** 전역이 덮던 것 중 실제로 위험한 것(키프레임 애니메이션·부드러운 스크롤)은 그대로 남고, 새로 컴포넌트 책임이 되는 것은 **`transform` 전환뿐**입니다. 그런데 `transform`은 애초에 전역 규칙으로 해결되지 않던 항목이라(이유 ②) **보호 범위가 줄지 않습니다 — 오히려 늘어납니다.**

#### 6-1a. 활성 내비는 배경만으로 표시하면 안 됩니다

`--color-accent-subtle`을 흰 배경에 합성하면 **`#fcf2e3`, 대비 1.11:1**입니다. 배경만 쓰면 라이트에서 활성 항목이 사실상 안 보입니다(다크도 1.15로 마찬가지).
→ **배경 + 밑줄을 함께** 씁니다. 시안의 판단이 정량적으로 옳습니다. 색을 구분하지 못하는 사용자에게도 밑줄의 위치가 남습니다.
활성 라벨 색은 `--color-accent-text` (합성 배경 위 **5.56:1**).

#### 6-1b. 스크롤 배경 전환 (홈 전용)

홈에서만 헤더가 투명하게 시작해 히어로 그래픽이 화면 끝까지 이어져 보이게 합니다.

```
scrollY = 0    → 배경 불투명도 35%, 하단 보더 없음
scrollY = 60px → 배경 불투명도 100%, 하단 보더 --color-border-strong
보더는 진행률 15% 지점부터 나타남
alpha = min(1, scrollY / 60);  bg = rgba(<raised RGB>, 0.35 + alpha * 0.65)
```
- raised RGB: 라이트 `255,255,255` / 다크 `22,29,48`
- **홈 외 페이지에서는 처음부터 불투명**합니다
- 헤더의 **위치·크기는 절대 변하지 않습니다.** 배경 불투명도만 바뀝니다 — 이것이 헤더가 하는 유일한 움직임이며, 히어로 그래픽과 시선을 다투지 않기 위한 제약입니다

#### 6-1c. 404에서의 경로 표시 (R-2 판정 · 2026-08-01)

**판정: 헤더 경로는 `~`로 고정합니다. 잘못된 경로를 헤더에 넣지 않고, 헤더를 숨기지도 않습니다.**

404에서는 헤더 경로와 본문 장식 라인이 같은 경로를 두 번 보여주는 문제가 있었습니다. 셋 중 하나를 골라야 했습니다.

| 안 | 판정 |
|---|---|
| 헤더 경로를 숨김 | ❌ 전 페이지 공통인 셸에 404만 예외를 만듭니다 |
| 본문 장식 라인 제거 | ❌ 404는 **위트가 허용되는 유일한 실패 화면**(WRITING_GUIDE §6.5)이고, 그 라인이 브랜드와 디버깅 정보를 동시에 담당합니다 |
| **헤더 `~` + 본문이 입력 경로 담당** | ✅ **채택** |

근거 셋입니다.

1. **터미널 은유가 정확해집니다.** `cd`가 실패하면 사용자는 **원래 있던 곳에 그대로** 있습니다. 헤더가 `~`를 보여주고 본문이 `▸ ~ cd <입력 경로>`(실패한 명령)를 보여주는 것이 은유상 옳습니다.
2. **헤더 경로는 "여기가 어디"를 알리는 표시**인데, 존재하지 않는 위치를 그 슬롯에 넣으면 사실과 다릅니다.
3. **셸에 예외가 생기지 않습니다.** 경로 슬롯은 모든 페이지에서 항상 채워집니다.

→ 사용자가 입력한 잘못된 경로는 **본문 장식 라인이 단독으로** 담당합니다. 중복이 사라지고, 오타를 눈으로 확인하는 실용적 가치도 그대로 남습니다.

### 6-4a. 🔴 전역 셸 공개 API — `openSearch()` (신규 · 차단 이슈 해소)

404의 `검색으로 찾기`처럼 **셸 밖의 화면이 검색 UI를 열어야 하는 경우**가 있습니다. 공개 API가 없으면 각 화면이 검색 UI를 중복 구현합니다. 셸이 아래 계약을 노출하세요.

```ts
// src/components/shell/ShellContext.ts
export interface OpenSearchOptions {
  /** 입력에 미리 채울 검색어. 채운 뒤 전체 선택 상태로 둡니다 */
  query?: string;
  /** 닫을 때 포커스를 돌려줄 요소. 생략 시 호출 시점 document.activeElement */
  returnFocusTo?: HTMLElement | null;
}

export interface ShellApi {
  openSearch(options?: OpenSearchOptions): void;
  closeSearch(): void;
  readonly isSearchOpen: boolean;
}

export function useShell(): ShellApi;
```

- Provider는 **`App.tsx` 레벨**에 둡니다 (헤더·푸터가 이미 그 자리로 승격돼 있음)
- frontend가 이미 동작시켜 둔 **`⌘K` 핸들러의 상태를 그대로 Context로 올리면 됩니다.** 새 UI를 만들 필요는 없습니다

**동작 계약**

| 상황 | 동작 |
|---|---|
| 데스크톱(≥1024) `openSearch()` | 헤더 인라인 입력 250→320px 확장 + 포커스 |
| 모바일(≤767) `openSearch()` | 전체화면 오버레이 + 입력 자동 포커스 + `body` 스크롤 락 |
| `openSearch({ query })` | 입력을 채우고 **전체 선택**(사용자가 바로 덮어쓸 수 있게) + 결과 즉시 표시 |
| 이미 열려 있을 때 재호출 | **새 오버레이를 만들지 않고** 입력에 재포커스. `query`가 있으면 교체 |
| `closeSearch()` / ESC / 닫기 버튼 | 닫고 **포커스 복귀** (`returnFocusTo` → 없으면 호출 시점 `activeElement`) |
| **라우트 변경** | 자동 `closeSearch()`. 404에서 검색 → 글 클릭 → 이동했을 때 오버레이가 남으면 안 됩니다 |
| `⌘K` / `Ctrl+K` | 셸이 전역 등록. **`input`·`textarea`·`contenteditable`에 포커스가 있으면 무시** |

**호출자**

| 화면 | 호출 |
|---|---|
| 404 `검색으로 찾기` | `openSearch()` |
| 글 목록 빈 상태 | STEP 4가 **자체 인라인 입력**을 쓰면 호출 불필요. **전역 오버레이**로 결정되면 `openSearch({ query: 실패한검색어 })` |
| 그 외 | 위 계약을 그대로 사용 |

> **범위 주의**: 이 API는 **UI를 여닫는 것만** 책임집니다. 실제 필터링 로직은 STEP 4와 함께 붙습니다(§6-4). 현재 `usePosts`의 필터는 AND 완전일치라 결과가 항상 0이며 재작성 대상입니다.

- 히어로 주 CTA는 **홈에 1개만** 존재합니다. 다른 화면의 주 버튼도 Pretendard 15px입니다
- 22px 픽셀 라벨은 세로 여백이 커 보이므로 버튼 패딩은 `--space-3 --space-6`(12/24) 기준으로 잡고 시각 보정하세요
- 버튼 라벨에 `font-weight`를 픽셀 서체에 주지 마세요 (§4-2)

### 6-8. 헤더 ↔ 히어로 겹침 규칙 (STEP 2 정합 · 신규)

STEP 2가 히어로 높이를 `svh` 기반 `clamp()`로 확정했고(§6-8a), 그 높이가 **헤더를 포함한 첫 화면 점유율**이어야 합니다. 그러려면 **헤더가 히어로 위에 겹쳐야** 합니다.

현재 §6-1은 헤더를 `position: sticky; top: 0`으로 두는데, sticky는 **문서 흐름에서 자리를 차지**합니다. 그대로 두면 히어로가 헤더 아래에서 시작해 §6-1b의 "투명하게 시작해 그래픽이 화면 끝까지 이어져 보이게"가 성립하지 않습니다.

**해법 — 헤더는 sticky 유지, 히어로만 끌어올림 (홈 전용)**

```css
/* 홈의 히어로에만 적용 */
.hero {
  margin-top: calc(-1 * var(--header-h-desktop));  /* sm에서는 -mobile */
  padding-top: var(--header-h-desktop);            /* 텍스트가 헤더 밑에 깔리지 않게 */
}
```

- `position: fixed`로 바꾸지 마세요. 그러면 **모든 다른 페이지**에 `padding-top` 보정이 필요해집니다. 음수 마진은 홈 한 곳만 건드립니다
- 헤더 `z-index: var(--z-header)`가 히어로 캔버스보다 위 (§3-4)
- 겹침 결과: 첫 화면에서 **히어로 높이 = 헤더 + 그래픽**. STEP 2의 `56svh`가 곧 헤더 포함 점유율이 됩니다

#### 6-8a. 히어로 높이 — STEP 2 값 채택

| bp | 높이 |
|---|---|
| xl (≥1280) | `clamp(440px, 56svh, 560px)` |
| lg (1024~1279) | `clamp(400px, 54svh, 500px)` |
| md (768~1023) | `clamp(380px, 52svh, 460px)` |
| sm (≤767) | STEP 2 §7.2 2존 구조 |

- `agent-log/design.md` Part II-D의 `xl 70vh`는 **폐기**합니다. 1440×900에서 70vh = 630px로, 첫 화면이 그래픽으로만 차 "30초 안에 읽을 글 파악"이라는 주 과업을 방해합니다
- **`vh`가 아니라 `svh`를 씁니다.** 모바일 브라우저에서 `100vh`는 주소창이 **숨겨진** 상태 기준이라 주소창이 보일 때 히어로가 화면을 넘칩니다. `svh`는 주소창이 보이는 상태 기준이라 최악의 경우에도 의도한 비율이 지켜집니다
- 폴백: `height: 56vh; height: 56svh;` 두 줄을 순서대로 쓰면 구형 브라우저는 앞줄을 씁니다

**역할 분담 규칙**

| 대상 | 수단 | 이유 |
|---|---|---|
| 레이아웃·타이포·간격·표시 여부 | **CSS 미디어쿼리** | 첫 페인트부터 정확. `useMediaQuery`는 첫 렌더에서 `false`를 반환해 레이아웃 플래시를 만듭니다 |
| DOM 구조 자체가 달라야 함 | **CSS 우선 시도** → 불가할 때만 JS | 드로어·오버레이는 CSS로 처리 가능 |
| JS가 뷰포트를 알아야 함 (스크롤 숨김 활성 여부 등) | `matchMedia` 직접 사용 | |

**정리 대상 (현재 코드)**
- `ResponsivePC`와 `ResponsiveTabletPC`가 **완전히 동일한 JSX**를 렌더합니다 — 조건부 분기가 아무 차이를 만들지 않으면서 트리만 2배입니다. 통합하거나 제거하세요
- 내비게이션은 **`<ul>` 하나**를 두고 CSS로 배치만 바꾸세요. 지금처럼 데스크톱용·모바일용 메뉴가 DOM에 둘 다 있으면 스크린리더가 메뉴를 두 번 읽습니다

브레이크포인트 숫자는 CSS와 JS 양쪽에 존재할 수밖에 없습니다(CSS 커스텀 프로퍼티는 `@media`에서 못 씀). `src/styles/breakpoints.ts`에 상수로 두고, **위 표를 계약 원본**으로 삼으세요. `postcss-custom-media` 도입 여부는 frontend 판단입니다.

### 14-1a. STEP 5 반영 필요 — 2026-08-01 판정 3건

| # | 항목 | 판정 |
|:--:|---|---|
| A | **404 이탈 별 점선 가림** | **`drift` 0.6 → 1.2 cell**(데스크톱 24px). 아래 공식 참조 |
| A-2 | **빈 자리 윤곽이 안 보임** | 윤곽을 **`--color-border-interactive`** 로. A와 **함께 적용해야** 조건 4 성립 |
| B | **격자 연결선 `-weak` → `-strong`** | ✅ **추인.** 되돌리지 마세요 |
| C | **404 헤더 경로** | 헤더는 `~` 고정, 본문 장식이 입력 경로 담당 (§6-1c) |
| D | **잔디 셀 툴팁 명세 오류** | frontend 지적 타당. **명세를 고치세요** |

**A. 점선이 읽히는 최소 간격 — 공식**

> **가시 간격 = 중심거리 D − (r₁ + r₂) ≥ 10px**

10px의 근거: 점선이 "끊어진 연결"로 읽히려면 **대시 2개 + 사이 간격**이 필요합니다(2+2+2 = 6px). 여기에 양 끝이 원에 닿지 않도록 2px씩 여백(4px)을 더해 **10px**입니다.

현재: D = `0.6 × cell` = **12px**, r₁+r₂ = **13px** → 가시 간격 **−1px**. 원이 오히려 겹칩니다.
필요: D ≥ 13 + 10 = **23px** → `drift ≥ 23 / 20 = 1.15 cell`

**→ `drift` 0.6 → `1.2` (데스크톱 24px, 가시 간격 11px)** 를 권합니다. 여유 1px를 두어 반지름이 조금 바뀌어도 견딥니다.

- **반지름을 줄이는 대신 `drift`를 늘리는 이유**: 반지름 13px은 이탈 별이 "별"로 읽히는 최소 크기에 가깝고, 줄이면 그래픽이 약해집니다. 위치는 조정해도 조형이 약해지지 않습니다
- **1.2 cell은 격자 한 칸 남짓**이라 "한 자리 어긋난 별"로 읽힙니다. 구도가 무너지지 않습니다
- **저감 모션에서는 `drift`를 최대값 1.2에 고정**하세요. 정지 상태에서 끊긴 연결이 가장 잘 읽혀야 합니다(조건 4)
- 모바일 등 `cell`이 다르면 공식으로 재계산하세요 — 값이 아니라 **공식이 명세**입니다

**A-2. 빈 자리 윤곽 대비 — `--color-border-strong` → `--color-border-interactive`**

`drift`만 고쳐서는 부족합니다. QA 실측대로 윤곽이 **라이트 1.40 / 다크 1.58**이면 "여기 뭔가 있어야 한다"를 담당하는 유일한 요소가 안 보입니다. **두 수정은 함께 적용해야 조건 4가 성립합니다.**

| | 이전 `--color-border-strong` | **확정 `--color-border-interactive`** |
|---|---:|---:|
| 라이트 | `#cfc9ba` **1.40** | `#7d7768` **3.78** |
| 다크 | `#2d3551` **1.58** | `#6d7798` **4.32** |

- **새 토큰을 만들지 않았습니다.** `--color-border-interactive`는 이미 "이 경계는 반드시 지각되어야 한다"는 역할로 정의된 토큰이라 의미가 정확히 맞습니다
- 양 모드 모두 **2.7배** 개선되고, 라이트가 상대적으로 더 약하던 문제도 함께 좁혀집니다
- **골드 별과의 위계도 맞습니다** — 별은 다크 8.93 / 라이트 6.16이라 윤곽의 약 2배입니다. 별이 주인공이고 윤곽은 명확하되 종속적이라는 관계가 유지됩니다
- 순수 장식(`aria-hidden`)이라 WCAG 1.4.11 비적용이고 **눈으로 읽히는지가 유일한 기준**이라는 기존 판정 그대로입니다

> `--color-text-muted`(5.3~5.6)까지 올리면 윤곽이 별과 대등해져 시선이 분산됩니다. `border-interactive`가 상한입니다.

**B. 연결선 색 추인 근거**

`-weak`(α .11)는 홈 히어로의 **빽빽한** 성좌에서 "약한 연결"로 설계된 값입니다. 404 격자는 요소가 성겨 같은 알파가 배경에 묻힙니다. **밀도가 다르면 필요한 알파도 다릅니다.** 게다가 404 격자에서 이 선은 약한 부가 정보가 아니라 **주 구조**이므로 `-strong`이 의미상으로도 맞습니다. 새 토큰은 만들지 마세요.

**D. 잔디 셀 툴팁 — 명세 오류 정정**

데이터 계약상 `days[i]`는 **레벨 0~4이지 기여 횟수가 아닙니다.** `2025.05.26 · 4회`는 **거짓 정보**입니다. frontend가 날짜만 넣은 것이 옳습니다.

| | |
|---|---|
| ❌ 폐기 | `2025.05.26 · 4회` |
| ✅ 확정 | `2025.05.26` (날짜만) |
| 대안 | 횟수를 정말 보여주려면 **데이터 계약에 `count`를 추가**해야 합니다. 레벨에서 횟수를 역산하지 마세요 |

집계 수치는 이미 §6-2 요약 라인(`최근 1년 ⟨N⟩회`)이 담당하므로, 셀 단위 횟수가 없어도 정보 손실은 없습니다.
